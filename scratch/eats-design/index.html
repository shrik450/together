Decisions for you

These choices change what I'd build. Each one has my recommendation. The rest of the page assumes the recommendation, and says where a different answer would change it.

1. Coordinates come from the Maps link; drop the address and Nominatim

The spec stores an address so Nominatim can geocode it for the map. But once the browser waits for the Maps page to finish loading, the Maps URL itself carries the place's exact pin (!3d…!4d…). Nothing else would use the address: we don't filter, sort or map on it, and the place page already links to Maps.

Recommend: no address field and no Nominatim. A place gets coordinates from its Maps link; a place with no Maps link doesn't show on the map until it has one. This removes a third-party service, its rate limit and a queued geocoding job from milestone 5.

2. One place per Maps place, enforced

The spec says adding a place whose Maps link we already have warns. The Maps URL contains a stable feature ID (0x89c2598f7ff4aa09:0x313547e757cb8cea), the same whichever phone or link format it came from. Two records for one feature ID are always a mistake.

Recommend: maps_feature_id is unique on places. Pasting a known place's link shows "You already have Katz's Delicatessen" with a link to it, rather than a warning you can click through. Merging still handles duplicates that slipped in without a Maps link.

3. Search with LIKE, not SQLite FTS5

Search covers place names, notes, dish names and takes. FTS5 means a virtual table, triggers to keep it in sync, and a second place that has to filter out unrevealed takes. Two people will have hundreds of places, not hundreds of thousands, so a case-insensitive substring match across four columns returns instantly.

Recommend: LIKE queries, with places whose names match ranked first. FTS5 is the upgrade path if we ever want stemming or ranking, and the search function's interface won't change.

4. Place URLs are /eats/places/{id}/

docs/architecture.md sketches /eats/<place-id>/. Eats also has tags, visits, rounds and an inbox, so bare numbers at the top level would share a namespace with words like inbox.

Recommend: /eats/places/{id}/, /eats/tags/{name}/, /eats/visits/{id}/ and so on, and update the architecture doc's example.

5. Merging deletes the merged-away place

After a merge, everything belonging to the duplicate (links, tags, interest, visits, dishes, round candidates) moves to the place we keep, and the duplicate is deleted. A bookmark to the deleted place's URL then shows "not found".

Recommend: delete it, with no redirect. Duplicates will be rare and young, so they're unlikely to be bookmarked. The database then checks the merge for us (see invariants).

6. "Time waited" means since added or last visited

Sorting and quick pick both use "how long a place has waited", which the spec doesn't define.

Recommend: time since the later of the place being added and its last visit. Logging a visit doesn't change anyone's interest; it restarts the wait.

What the Maps check found

The spec leaves open how reliably Maps links resolve to coordinates. An earlier test said the address bar never changed. I opened a Maps search link in the framework browser again and read the address bar every 1.5 seconds:

0 /maps/search/?api=1&query=Katz's+Delicatessen+New+York 1 /maps/search/?api=1&query=… 2 /maps/search/?api=1&query=… 3 /maps/place/Katz's+Delicatessen/@40.722233,-73.987429,17z/data=!3m1!4b1!4m6!3m5 !1s0x89c2598f7ff4aa09:0x313547e757cb8cea!8m2!3d40.722233!4d-73.987429!16z… title: "Katz's Delicatessen - Google Maps" text: … 205 E Houston St, New York, NY 10002 …

Maps rewrites the URL about four seconds after load. BrowserService.fetch takes its snapshot once the page's text stops changing, which is earlier, so that's why the first test missed it. Once the URL has changed, it gives us:

  • Identity: the feature ID after !1s, the same however the link was shared.
  • Coordinates: the pin, from !3d (latitude) and !4d (longitude). The @ part is where the map is centred, which isn't always the pin.
  • Name: the page title, minus " - Google Maps".

A ?cid= link and a bare /maps/place/Name link didn't load a place within the probe's time limit. A search that matches several places stays on /maps/search/, so no single place is found. I couldn't test the links our phones actually share (maps.app.goo.gl/…). Please send me three or four real share links from each of your phones before I build the lookup.

The framework change this needs is small: fetch takes an optional condition on the URL and keeps waiting, up to a limit, until the URL meets it (below).

Module shape

Eats is a normal module under modules/eats/, registered in app.py like home. It splits into a functional core and an imperative shell. The core is the rules: who sees which take, how a round ends, how picks are weighted, what a Maps URL means. Those are pure functions of plain values, unit-tested. The shell is handlers, queries and jobs that read the database, call the core, and write the results back. It's tested end to end against a real SQLite database.

Core (pure, unit-tested)

  • links.link_kind(url): Google Maps, website, Yelp, Instagram or other
  • maps.parse_maps_place(url, title): feature ID, pin and name
  • takes.visible_takes(...): the reveal rule
  • dishes.dish_board(...): each person's latest verdict per dish
  • dishes.dish_key(name): the name used to match dishes
  • picking.quick_pick / random_pick: weighting, with a seeded Random passed in
  • rounds.round_state(...): whose turn it is, and the result
  • finding.waited(...): time waited

Shell (integration-tested)

  • handlers/*: parse forms, call queries, render templates
  • places.py: create, edit, archive and merge places, all in one transaction
  • finding.py: builds the select for filter, sort and search
  • maps.look_up(url): opens the link in the framework browser
  • proposals.py, jobs.py, llm.py: capture

Reading and writing

  • No ORM relationships. Models declare columns and foreign keys only. Reads are explicit selects, so async code never lazy-loads by accident, and every page's queries are visible in one function.
  • Templates get view dataclasses, not ORM rows. finding.py and friends return frozen dataclasses like PlaceCard and PlaceDetail. Takes leave the database only as TakeView, whose text is None until the take is revealed, so no template can show text it shouldn't.
  • Handlers stay thin. They parse the form (Litestar's dataclass DTOs, or plain Body parsing), call one write or query function with the request's db_session and current_user, then render or redirect. Mutations are explicit form posts (POST then redirect). HTMX swaps fragments for the interest toggle, search-as-you-type and the Maps lookup.
  • "Both of us" means every user. The reveal and round rules take the set of user IDs as an argument, so they're pure and testable. The shell reads it from users. With exactly two users that's the two of you; the rules check the count, so a third account fails clearly rather than quietly.

Invariants and what enforces them

Where possible the database or a type enforces a rule, so it doesn't depend on every handler remembering it.

RuleEnforced by
One record per Maps placeUnique maps_feature_id
A merge moves everything, or nothing happensEvery foreign key to eats_places is ON DELETE RESTRICT (SQLite already runs with foreign_keys=ON). The merge moves children and then deletes the duplicate, in one transaction. If a later milestone adds a table that references places and merge isn't taught about it, the delete fails and the transaction rolls back, so nothing is lost silently.
Merging dishes keeps every verdictDishes with the same key are combined by moving verdicts to the kept dish. Verdicts can't collide, because each visit belonged to only one of the two places.
One take, interest or verdict per personComposite primary keys
Take text stays hidden until both have written onetakes.py is the only code that reads take text. Pages get TakeView(text=None), and search and the capture agent use the same readable_takes(viewer) SQL condition.
Nothing from an LLM becomes a record until confirmedAgents only write eats_proposals.output. Records are created only by proposals.confirm(), in one transaction.
Proposal output is well-formedParsed with a TypeAdapter[Capture] on the way in and out, following the untyped-library rule
Coordinates are both set or both emptyCHECK ((latitude IS NULL) = (longitude IS NULL))

How the main flows work

Add a place from a Maps link M1

Looking up the link shows you a result but saves nothing, so it runs inside the request rather than as a queued job, following the framework's rule. It takes around five seconds.

You
On /eats/places/new, paste a Maps link into the link field.
HTMX
hx-post /eats/places/lookup on paste or change. The field shows "Opening Maps…" and is disabled meanwhile.
Handler
maps.look_up(url) calls browser.fetch(url, wait_for_url=is_maps_place_url), then the pure parse_maps_place(page.url, page.title).
Handler
If the feature ID is already saved, return "You already have Katz's Delicatessen". Otherwise return the form section with the name filled in, and the feature ID and pin as hidden fields, ready to edit.
You
Adjust the name, add tags and "want to go", then Add place (a normal POST that redirects to the place page).
If it fails
Search blocked, timeout, or no single place found: an inline note says so, and you can still type a name and save. The link is kept, and the place simply has no pin.

The hidden fields come back from the client, so the POST rechecks them: parse_maps_place runs again on the submitted Maps URL, and the unique constraint catches a race. A tampered pin could only misplace our own place.

Browse and search M1

GET /eats/places/?interest=both&tag=georgian&visited=no&sort=waited&q=dump. Every filter is a query parameter, so each view has its own URL. finding.find_places(session, viewer, Filters) builds one select and returns PlaceCards. The search box uses hx-get with a short delay and swaps in just the list. Quick pick, random pick, decision rounds and the map all start from the same Filters, so a filter works the same everywhere.

Log a visit and reveal takes M2

visit logged→ one take written→ both written: revealed

While a visit is waiting on your take, it sits in the "How was it?" panel on /eats/. When you've written yours and the other person hasn't, you see their "would return" but not their text: "Samhita hasn't written hers yet." Takes stay editable after they're revealed.

def visible_takes(
    takes: Sequence[Take], viewer_id: int, user_ids: frozenset[int]
) -> Sequence[TakeView]:
    revealed = {take.user_id for take in takes} == user_ids
    return [
        TakeView(
            user_id=take.user_id,
            would_return=take.would_return,
            text=take.text if revealed or take.user_id == viewer_id else None,
        )
        for take in takes
    ]

Decision rounds M3

A round starts from the browse page's current filters. While a round is open, it shows on /eats/ for both of you. While you wait for the other person, the round page checks back with HTMX every 10 seconds. round_state(rule, candidates, answers, user_ids) is pure and returns one of these:

Both swipe deal ~8→ answering→ both done → matches→ tap one → decided
no matches → no match→ deal again (deal 2) → answering
Propose and pick shortlisting→ starter submits 2–5 → picking→ other picks → decided

Your answers aren't shown to the other person until the round reaches matches or decided. A decided round offers Log a visit for today, an explicit POST that creates the visit, which then shows up in "How was it?". Quick pick weighs places both of you want ×2, then by 1 + days_waited / 30, and picks three without repeats. The random source is passed in, so tests can fix it.

Capture with an LLM M4

queued→ job starts → working→ ready→ confirm (with edits) → records created
↘ error, or still working after 10 min → failed→ retry →queued
  1. Writing freeform text, adding by name, pasting a link or uploading a receipt creates an eats_proposals row (status queued), then calls scheduler.enqueue(jobs.work_on_proposal, proposal_id) and redirects to the inbox. A receipt image is stored on the row rather than in the job's arguments, so it can be cleared once read.
  2. The job sets the proposal to working and runs capture_agent with run_agent. The agent has the framework's web_toolset and an Eats toolset: find_saved_places(query), which returns IDs, names, tags and dish names but never takes, and look_up_maps_link(url), which reuses maps.look_up. On success it stores the parsed Capture and clears the image. On failure it stores the error and keeps the image so a retry can use it.
  3. The inbox checks back every few seconds while anything is queued or working. A proposal still working ten minutes after it started is shown as failed, because a restart might have killed its job and jobs aren't rerun.
  4. Confirming renders the proposal as a prefilled form; submitting creates every record in one transaction and deletes the proposal.

The agent's output type Capture refers to existing places by ID and to new ones by name, so the same type covers a single new place from a link and a whole evening from a text message.
